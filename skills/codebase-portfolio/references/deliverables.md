# Deliverables, in order, and what makes each one good

Each section says what the deliverable is, where it goes, and when it is done. Skip or merge
to fit the repository.

## M1. Private mirror

GitHub cannot make a private fork of a public repository. Instead:

```bash
gh repo create <owner>/<project>-portfolio --private
git remote add portfolio <ssh-url>
git push portfolio main
```

- `origin` stays upstream. All work is on branches off `main` in the mirror.
- One branch per future pull request, named for it (`portfolio/case-study`).
- One `portfolio/private` branch for material that never goes upstream: gated figures, the
  role statement, the demo script. It is never the base of an outgoing branch.
- Push named branches only. Untracked scratch in the working tree stays untracked.
- A scheduled CI trigger will also run in the mirror; leave it unless the minutes matter.

Done when the mirror's `main` matches upstream and CI is green there.

## M2. Hygiene

- **Licence.** If there is none, open an issue asking the maintainers to choose one, and
  write "licence pending" wherever the portfolio would otherwise state it.
- **Sensitive findings.** Replace with the placeholders the repo already uses. Report whether
  history is affected and leave the rewrite decision to the maintainers.
- **Stale links and wrong snippets** met during exploration. They are small, and a reviewer
  who hits a dead link in the first minute stops reading.

Done when the issue is raised and one small pull request carries the fixes.

## M3. Case-study page

One new page (in the docs site if there is one, otherwise a section at the top of the
README), linked from a short "Start here" block. Existing pages are not rewritten.

Sections: problem, approach, architecture, what runs where, results, contributors and roles,
limitations and roadmap.

**Reading paths.** One per audience, each about five links and five minutes, each link with
one line on what the reader will see there. Typical audiences for a research-software project:

| Audience | Wants to see | Path usually runs through |
|---|---|---|
| Engineers in the field | The core idea working; sound design choices; tests | runnable notebook → concept page → one design decision record |
| Infrastructure / operations | Scale, failure handling, measurement | architecture → a scaling or acceptance record → a post-mortem |
| Program and product managers | Scope, decisions, collaborators, outcomes | tracker with evidence-closed items → decision index → roadmap → contributors |

**Architecture diagram.** Mermaid, kept in the page, derived from the existing architecture
docs so the two cannot disagree.

**Contributors table.** From `scripts/authorship_by_area.sh`. State the owner's role in one
sentence the table supports.

**Limitations.** What does not exist, in plain words, with the nearest thing that does.

Done when the page is in the nav, the docs build passes in strict mode, and every path link
resolves.

## M4. One-command demo

A thin wrapper — a `Makefile` target or a script — over commands that already exist:

- creates an isolated environment and installs in the order the project's own setup uses;
- runs the laptop demos found in exploration;
- writes outputs to one ignored directory and prints the list of files written;
- has a companion target that runs the tests covering those demos.

Add a CI job that runs it and uploads the outputs, so "one command, under N minutes" is
checked on every push rather than asserted. No container unless a reviewer needs one.

Done when a fresh clone produces the figures with one command inside the stated time.

## M5. Guided tour notebook

One notebook, committed with outputs, rendered by whatever the docs site already uses.

- Each section shows one idea: the core behaviour, the same idea at larger scale, one
  reliability property, one integration.
- It imports existing helpers only. If a section would need new logic, replace it with prose
  and a link to the test that exercises the behaviour.
- Section titles use the honest name of what is shown.
- Register it with the existing notebook check. Advertise a hosted-runtime badge only after
  someone has run it there.

Done when it executes under the project's notebook check and renders on the built site.

## M6. Results

**Stage A, public.** A page that gathers numbers already in the public repository, each with
its job ID or commit and a link to the record that produced it. Hardware stated once. Nothing
new is measured or revealed.

**Stage B, gated.** On the private branch: a performance page built from the fuller analyses,
figures regenerated by their existing scripts from a trimmed copy of the data (only the
columns each figure reads; large tables stay out of git), vector output plus PNG, in the
project's plot style. It moves toward a public branch only after the owner records approval.
Until then the case study links Stage A.

Done when every number on Stage A can be checked against its source, and Stage B's figures
regenerate from the trimmed data.

## M7. Private narrative assets

On the private branch, not for upstream:

- **Role statement.** One paragraph for a resume or profile. Every claim is tied to a commit
  range, a document or a row of the contributors table.
- **Demo script.** A two-minute shot list with narration: the one command, one figure that
  shows the system changing course, one real-run result from Stage A.
- **One-page brief.** For readers who will not open the repository: scope, timeline,
  collaborators, outcomes.

## M8. Upstream and sign-off

Open the pull requests in milestone order — hygiene, case study, demo, notebook, results —
each reviewable in ten minutes, each saying what a reviewer can run to check it. Rebase on
upstream before opening each. After they merge: scan upstream's default branch again, confirm
the docs site deployed, and update the links the owner hands out. Stage B follows when
approval arrives.

If the decision was to make the mirror public instead, the same order applies to merging into
its `main`, and the visibility change is the last step, after the scan.
